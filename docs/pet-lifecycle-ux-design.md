# 宠物预设生命周期 UX 设计（pet-lifecycle-ux-design）

> 2026-09-01，从用户心智模型出发的宠物预设生命周期 UX 设计。本文只设计、不动工；
> 所有现状论断均经代码核实并附 file:line。前置阅读：`docs/preset-authority-eval.md`
> 评估一（架构现状与翻转方案）、`docs/deferred-backlog.md` C5/C2 条目。
>
> 结论速览：
> - **心智模型定调**：「预设是名字簿，配置是本体」——用户编辑的永远是当前这只宠物的本体；保存 = 写回名字，切换 = 换一只本体。现状之乱源于「没有名字的本体」（activePetId=null）被当成一只宠物列进选择器，叠加四套不一致的 dirty 策略与删除死局。
> - **删除**：维持「生效宠物禁止删除」的 host 409 拍板（不推翻），补「管理宠物」列表让非生效宠物可删（backlog 已登记的缺口，本文给出设计稿）；「删除生效宠物 = 自动回落」留给预设权威化落地时重议。
> - **dirty 统一原则**：草稿永不静默丢失——能前置阻止的入口阻止并给出路，不能阻止的出口用系统级守卫，一切确认走 C2 模态。卡片卸载 `window.alert` 残留移除，改常驻可见提示。
> - **「未命名宠物」自动 fork 惯例不恢复**（已于 2026-08-22 移除且被 dirty 门取代）；「未保存的当前配置」改名「未命名配置」与 dirty 的「未保存修改」解撞词。
> - 全部推荐分「可先行」（两架构皆成立，零 host/零数据变更）与「随预设权威化」两批，逐条带 S/M/L 量级与涉及模块。

## 0. 现状速查：生命周期各环节的真实行为

> 每个环节按「用户做什么 → 看到什么 → 数据发生什么」盘点。此节是后续设计的共同事实基础。

### 0.1 数据关系（架构前提）

- 权威方是全局 config（`$DSH_HOME/petween/config.json`），预设是镜像；唯一镜像方向 = config 保存时把切片 `{scale, poses, states}` 写回活跃预设（`src/index.ts:56-61` 的 `onSaved` 接线；切片定义 `src/host/pets.ts:205-207`；边界声明 `src/host/pets.ts:4-9` 头注释）。
- `activePetId: string | null`；null = 「当前 poses/states/scale 是不属于任何预设的未保存编辑」（`src/core/types.ts:163-168`）。
- 反向（preset → config）只有三个入口，均自带完整切片：`POST /pets/<id>/apply`（`src/host/routes.ts:854-862`）、`POST /pets from:'current'/'blank'`（`src/host/routes.ts:684-696`）、宠物包导入最后一步（`src/host/routes.ts:789-795`）；裸 PUT 切 activePetId 会被展开为目标预设切片（`src/host/routes.ts:474-495`，2026-08-29 事故止血）。

### 0.2 创建（三个入口）

| 入口 | 用户做什么 → 看到什么 | 数据发生什么 |
| --- | --- | --- |
| 新建空白 | 点「新建空白」→ C2 模态输名字（`PetweenSettings.tsx:232-235`）→ 当前屏幕换成空宠物 | host 建空切片预设并 apply：`createPet(name, {})` + `updateConfig(applyPatchFor(pet))`（`routes.ts:692-696`）；旧切片被空切片覆盖 |
| 新建副本 | 点「新建副本」→ 输名字 → 当前屏幕不变（内容相同、身份已切换） | host 把**已保存的**当前切片存为预设并激活（`routes.ts:685-691`） |
| 另存草稿为新宠物 | 点「另存草稿为新宠物」→ 输名字（默认「<当前名> 变体」）→ notice「已另存为新宠物」→ 继续编辑原宠物 | `from:'draft'`：客户端草稿（含未保存修改）严格校验后建**新**预设；不切换、不动活跃宠物、不隐式保存（`routes.ts:653-680`、`editor-store.ts:872-893`） |

dirty 门：新建空白/副本要求草稿干净，否则 warn「有未保存修改，请先点击保存再操作宠物预设。」（`editor-store.ts:957-970`）；「另存草稿」dirty 可用（`editor-store.ts:872` 注释明示「unsaved edits included」）。

### 0.3 切换

下拉「当前宠物」选择目标（`PetweenSettings.tsx:255-268`）→ host 用目标预设完整切片覆盖 config（`applyPatchFor`，`pets.ts:210-228`；缺席的动画引用编码为 null 清空前任引用）→ client 以返回的完整 config 替换草稿并广播（`adoptPetConfig`，`editor-store.ts:973-983`）。dirty 或上次保存失败时被门拒（`editor-store.ts:960-968`）。

### 0.4 编辑与保存

任何控件改动 → `updateConfig` 就地改草稿、标 dirty、Live Preview 即时跟随（`editor-store.ts:363-373`）→ 顶部 SaveIndicator 显示「有未保存修改」（`PetweenSettings.tsx:150-159`）。点「保存修改」→ PUT 编辑器所有的六段（`editor-store.ts:1086-1093`，所有权注释 :1062-1066）→ host 原子写 config，随后锁段外镜像写活跃预设（`src/index.ts:59-61`；`saveSlice` 对内容未变的写入跳过，`pets.ts:457-473`）。**activePetId=null 时保存只写 config，没有镜像目标。**

### 0.5 重命名与署名

- 重命名活跃宠物：走 dirty 门；非活跃宠物：不读不写草稿、跳过 dirty 与保存失败门（`preparePetAction` 的 `touchesActive` 判定，`editor-store.ts:957-963`）。
- 署名：只要求存在活跃宠物（activePetId≠null），不看 dirty（`editor-store.ts:823-840`）；无活跃宠物时 warn「当前是未保存配置，选中一只宠物后再保存署名。」（:826-828）。

### 0.6 导入与导出

- 导出：仅活跃预设可打包；activePetId=null 时 warn「当前是未保存配置，选中一只宠物后再导出。」（`editor-store.ts:710-716`）。zip 反映**已保存的**预设，dirty 草稿不打包（:704-709 注释）。
- 导入：选 zip → dirty 时先经 C2 模态确认「…当前未保存的修改将被丢弃。要继续吗？」（`editor-store.ts:761-768`）→ host 资产 → 动画 → 建宠物 → 立即 apply，失败尽力回滚（`routes.ts:710-801`）→ client 全量 reload + 显式结清草稿记账（`editor-store.ts:786-792`）→ notice 汇总「已导入宠物「X」并切换」（:797-813）。

### 0.7 删除（现状死局）

- host：`DELETE /pets/<id>` 对当前 activePetId 返回 409 `ACTIVE_PET`（`routes.ts:896-909`，C5 方案 a）；非生效宠物删除成功，仅删 `pets/<id>.json` 文件（`pets.ts:476-484`），图片资产与动画库不动。
- UI：宠物卡的「删除」按钮按构造只作用于**活跃宠物**（`deleteActive` 只传 `active.id`，`PetweenSettings.tsx:243-247`），方案 a 下恒禁用（:293-300）。hint 写「生效中的宠物不能删除，请先切换到其他宠物」（:317-319），但切换后该按钮依然只指向新的生效宠物——**照做也删不掉任何宠物**。store 的非活跃删除通路（`editor-store.ts:922-933`，经 `preparePetAction(id)` 跳过 dirty 门）在 UI 层无任何入口。此即 backlog 登记的遗留缺口（`deferred-backlog.md:161-164`）。

### 0.8 关闭编辑器 / 卡片

- 独立编辑器页：dirty/saving/error 时挂 `beforeunload` 守卫（`PetweenSettings.tsx:702-711`）。
- DSH 设置对话框内的 PetweenCard：DSH 拆除对话框无可 veto 的关闭事件（`PetweenCard.tsx:35-36` 注释），卸载清理对脏草稿 `window.alert` 告知丢弃（:41-43）——IAB 中静默失效，模态替代不了（`deferred-backlog.md:153-154`）。

### 0.9 关于「未命名宠物」自动保存惯例的核实结论

任务背景与部分用户记忆中「activePetId=null 时新建/应用前会自动把当前切片存为『未命名宠物』」——**该行为已不存在**。时间线：2026-08-21 V1.1 初版确有此自动 fork（`implementation-notes.md:469`）；2026-08-22 配置改手动保存时移除，改由「切换遇未保存修改提示先保存」兜底（`implementation-notes.md:473`），并有测试锁定「from=blank / apply 均不再创建隐式未命名预设」（`tests/host/routes.test.ts:942`、`:1084`）。现状是 §0.2/§0.3 的 dirty 门。

## 1. 一句话心智模型与「乱」从何来

### 1.1 推荐的一句话心智模型

> **只有一只「当前宠物」：预设列表是它的名字簿，编辑器里的配置是它的本体。你改的是本体；「保存修改」把本体写回名字；「切换」把另一个名字的本体换上屏幕。另存 = 给当前样子起个新名字，不动手里这只。**

这个模型在两种架构下都成立：今天「本体」恰好由 config 承载、名字只是镜像（§0.1）；翻转后名字即本体（`preset-authority-eval.md:59-70`）。模型本身不暴露架构，只暴露**一个**第一公民——当前宠物。

### 1.2 现状的认知负担点（逐条对应代码）

1. **「没有名字的本体」被当成一只宠物列在选择器里。** 下拉首项「未保存的当前配置」（`PetweenSettings.tsx:262`）与真实宠物并列，用户要理解「我正在编辑的东西有时候是宠物、有时候不是」；该状态下重命名/删除/导出/署名全部禁用且各有各的提示文案（`editor-store.ts:713-715, 826-828`；`PetweenSettings.tsx:283, 296, 305`）。
2. **两种「未保存」撞词。** 身份无归属（activePetId=null，每次保存照样落盘 config）叫「未保存的当前配置」；内容未落盘（dirty）叫「有未保存修改」（`PetweenSettings.tsx:153`）。两个概念共用「未保存」一词，hint 与 notice 读起来互相矛盾。
3. **一个「保存修改」按钮两种去向。** 有活跃宠物 = 写 config + 镜像进预设；无 = 只写 config。一段 60 余字的 hint（`PetweenSettings.tsx:317-319`）承载了全部概念解释，而它同时还在解释切换门槛、另存、删除三件事。
4. **创建三分支语义重叠。** 「新建副本」（已保存切片、切换、需干净）与「另存草稿为新宠物」（含未保存、不切换、dirty 可用）的差异要读两段 prompt 标题才能分辨（`PetweenSettings.tsx:221-230`）。
5. **dirty 保护策略四种并存。** 切换/新建 = 阻止（`editor-store.ts:960-963`）；另存草稿 = 放行（:872）；导入包 = 确认后丢弃（:761-768）；署名 = 免疫（:823）。用户无法预判下一个按钮会走哪一套。
6. **删除死局。** §0.7：hint 指引的动作（先切换再删）在当前 UI 里永远无法达成。这是「宠物/暂存宠物的删除逻辑有点乱」这条用户反馈的直接来源。

根源诊断：1+2+3 是「config 权威 + 预设镜像」架构把实现细节（本体可以没有名字）漏到了 UI；4+5 是功能逐批落地（A2、§12、C5）各自带了局部合理的策略，缺一条全局原则；6 是 C5 拍板只封了 host 与按钮、没补替代路径。

## 2. 删除入口与对象

### 2.1 设计目标

让「删除宠物」可达、可预期、不可逆但不误伤：任何已存预设都可被删除；生效中的宠物不因一次点击消失；删除后果（署名随预设消失、图片与动画保留）在确认前可见。

### 2.2 三方案对比（删除按钮出现位置 × 生效宠物的行为）

| | 方案 A：维持禁止 + 补非生效删除入口（推荐） | 方案 B：删除生效 = 自动另存当前配置后再删 | 方案 C：删除生效 = 回落到剩余宠物或默认 |
| --- | --- | --- | --- |
| 用户做什么 | 「管理宠物」列表对非生效行点删除；生效行删除钮禁用 | 对生效宠物点删除 | 对生效宠物点删除 |
| 看到什么 | 确认模态「确认删除宠物「X」？此操作不可恢复。」；生效行附说明「生效中的宠物需先切换再删除」 | 确认模态「当前配置将另存为新宠物「X 副本」，然后删除「X」」 | 确认模态「删除后将切换到「Y」」（无剩余时另有说辞） |
| 数据发生什么 | DELETE 200，仅 `pets/<id>.json` 消失；config/activePetId 不动 | from:'current' 建副本 → 激活副本 → 删旧：一次点击净效果是「改名」，且多一次隐式 fork | 删文件 + activePetId 重指 + apply 继任者切片：屏幕上的宠物**换脸**；无剩余时回落 null 或新建默认宠物 |
| 与既有纪律 | 完全符合「身份变更不隐式保存」（`editor-store.ts:950-956`）与手动保存 | 冲突：删除动作隐式创建了用户未必想要的预设（命名、垃圾预设、updatedAt 搅动） | 部分冲突：删除动作隐式搬动了 config 切片 |
| 风险 | 两步删除生效宠物（先切走再删）是特性不是负担：防止一次点击让屏幕上的宠物消失 | 「删除」产出新预设，心智模型破裂；误删场景反而更绕（想真删要删两次） | null 落点正是 C5 拍板否决的混乱源（旧行为记录 `deferred-backlog.md:158-160`）；回落换脸是隐式数据移动 |
| 改动量级 | **M**：client 宠物管理 UI（`PetweenSettings.tsx` PetPresetCard + `settings.module.css`）+ 确认与测试；host 零改动 | M：store 编排两步操作 + 文案；host 零改动 | M~L：host DELETE 语义变更 + 落点策略 + client 同步；且推翻 C5 拍板需重议 |

### 2.3 推荐与对「禁止」拍板的立场

**推荐方案 A。** 明确：本推荐**不推翻** 2026-08-31 的「禁止删除生效宠物」拍板——该拍板消灭的是「删除后 activePetId 置 null、屏幕配置仍是已删宠物数值」的假死落点（`routes.ts:897-901` 注释记录旧行为），方案 A 完整保留这层保护（host 409 不动）。本文推翻的是「禁止 + 无入口」的当前**组合状态**：backlog 在 C5 落地当日已登记「若意图是切走后再删，卡片需要非生效宠物的删除目标（如宠物列表逐行删除按钮）」（`deferred-backlog.md:161-164`），方案 A 即该登记的实现设计。

方案 B 否决理由：用「创建」实现「删除」，与 A2 确立的显式 fork 语义（`routes.ts:653-656` 注释）相悖。方案 C 现阶段否决理由：落点要么是 C5 否决过的 null，要么是新造概念（默认宠物）——但它**在预设权威化形态 (i) 下成为唯一自然形态**：activePetId 恒非空（`preset-authority-eval.md:65`），删除活跃预设结构上必须有继任者。故方案 C 不在当前架构落地，**登记为翻转时的重议项**，届时推荐：回落目标 = 最近 updatedAt 的剩余宠物；无剩余 = 自动建默认宠物（与形态 (i) 首跑默认宠物同一机制）。这也回答了 `preset-authority-eval.md:141` 开放问题 6 的落点选择。

### 2.4 删除入口的具体形态（方案 A 下）

- 宠物卡选择器下方加「管理宠物」折叠区（与「来源与署名」折叠区同款交互，`PetweenSettings.tsx:372-389`）：逐行列出全部预设，每行 = 名字、生效标记、重命名、导出、删除。
- 生效行：删除钮禁用 + 行内一句「生效中——切换到其他宠物后可删除」；重命名/导出可用（与现状能力一致）。
- 非生效行：删除可用，点后 C2 确认模态：「确认删除宠物「X」？该宠物的署名将一并删除；图片与动画保留在库中。此操作不可恢复。」（后果三元组说清。）
- 删除走既有 `store.deletePet(id)` 非活跃通路（`editor-store.ts:922-933`），不触碰草稿；列表刷新沿用 `refreshPetsSafely`。
- 空配置状态（无可用图）下 PetPresetCard 依然渲染（`PetweenSettings.tsx:797`），管理入口天然可达。

## 3. 未保存修改（dirty）保护策略统一原则

### 3.1 四场景现状盘点

| 场景 | 现状策略 | 代码 |
| --- | --- | --- |
| 切换宠物 / 新建副本 / 新建空白 | **阻止**：dirty → warn 请先保存；上次保存失败 → warn 先重试或撤回 | `editor-store.ts:957-970` |
| 删除 | 活跃 = host 409 禁止（与 dirty 无关）；非活跃 = 无 UI 入口，store 层不看 dirty | `routes.ts:896-909`；`editor-store.ts:957-963` |
| 导入宠物包 | **确认后丢弃**：dirty → C2 模态确认才继续；无人应答按取消结案 | `editor-store.ts:761-768`；`dialog-queue.ts:12-15` |
| 关闭编辑器 / 卡片 | 编辑器页 = **系统守卫** beforeunload；卡片 = 卸载时 `window.alert` 事后告知（IAB 失效） | `PetweenSettings.tsx:702-711`；`PetweenCard.tsx:34-46` |

### 3.2 统一原则（目标态）

> **草稿永不静默丢失。** 丢弃一条草稿只有两条合法路径：用户在 C2 模态里显式确认，或用户点「撤回修改」显式放弃。实现上三分：
> 1. **能前置阻止的入口用阻止，并且阻止时给出路**（告知怎么保住草稿：保存 / 撤回 / 另存为新宠物）。
> 2. **不能阻止的出口用系统级守卫**（beforeunload）；守卫也不存在的环境，让「关闭即丢弃」在 dirty 期间**常驻可见**，而非事后补一句可能到不了的提醒。
> 3. **一切确认走 C2 模态队列**（原生 confirm/prompt/alert 已清零，IAB 无原生通道）；无 ModalHost 的场景按取消结案（`dialog-queue.ts:12-15`），破坏性流程绝不在无人应答的确认上继续。

「阻止 vs 确认」的选择标准：操作是否**替换当前工作面**。切换/新建替换工作面且日常高频 → 阻止（防肌肉记忆误触）；导入包是文件选择器之后的显式意图 → 确认即可（现状已如此，维持）。删除非生效宠物不触碰工作面 → 确认即可。

### 3.3 逐场景行为表（目标态）

| 场景 | 目标行为 | 相对现状 | 量级 / 模块 |
| --- | --- | --- | --- |

### 3.4 卡片卸载 alert 残留处置

## 4. 「未命名宠物」自动保存惯例：保留 / 去除 / 改名

三个候选项其实是三个不同时态的东西，先厘清（核实结论见 §0.9）：

| 候选 | 含义 | 取舍 |
| --- | --- | --- |
| 恢复自动 fork（2026-08-21 旧行为） | 切换/新建前把 null 切片自动存为「未命名宠物」 | **不恢复**。手动保存 + dirty 门已覆盖它当年防的丢失（`implementation-notes.md:473`）；自动 fork 产生用户不认识命名的预设垃圾（「未命名宠物」「未命名宠物 2」），且与「身份变更不隐式保存」纪律（`editor-store.ts:950-956`）相悖 |
| 维持 null 草稿（现状） | activePetId=null 即「无归属的本体」，保存照写 config，命名是显式 fork 点 | **维持**。它是 A2「另存草稿为新宠物」无损分支的前提，也是评估一形态 (ii) 的语义（`preset-authority-eval.md:66`） |
| 改名（UI 文案） | 「未保存的当前配置」→「未命名配置（不属于任何宠物）」 | **推荐**。与 dirty 的「未保存修改」解撞词（§1.2-2）；「未命名」暗示「可以命名」，把用户引向另存/新建动作。量级 S（`PetweenSettings.tsx:262` 一处 + hint 同步） |

翻转落地形态 (i) 时，「自动建默认宠物」以新角色重生——不是恢复旧惯例，而是迁移/首跑的一次性兜底（`preset-authority-eval.md:65, 118`），推荐命名「未命名宠物（可改名）」。该决策随评估一开放问题 2 拍板，不在本批。

## 5. 另存为、重命名、导入导出：生命周期位置与文案原则

### 5.1 生命周期动线（目标态）

```text
        创建                         使用（生效中）                 维护            终结
 ┌──────────────────┐   ┌───────────────────────────┐   ┌──────────────┐   ┌──────────────┐
 │ 新建空白宠物并切换  │   │ 编辑 →「保存到「X」」（镜像写回）│   │ 重命名        │   │ 删除（管理列表， │
 │ 复制当前宠物并切换  │ → │ 另存草稿为新宠物（分叉不切换）  │ → │ 来源与署名     │ → │  仅非生效行）   │
 │ 导入宠物包（=建并切换）│   │ 导出宠物包（分享已保存的预设）  │   │              │   │              │
 └──────────────────┘   └───────────────────────────┘   └──────────────┘   └──────────────┘
        ↑ 另存草稿 = 创建但不离开「使用」区；导入包在生命周期里是创建入口（即导即用）
```

### 5.2 文案原则（五条）

1. **按钮名自带切换语义。** 「另存…为…」= 不离开当前；「新建/复制…并切换」= 离开。推荐：「新建副本」→「复制当前宠物并切换」、「新建空白」→「新建空白宠物并切换」；「另存草稿为新宠物」保持不变（已是家族里最自解释的）。**S**：`PetweenSettings.tsx:227-235`。
2. **保存的目标可见。** dirty 分支文案带当前宠物名：「保存到「女仆」」；无归属时「保存修改（未命名配置）」。镜像语义随之不言自明，hint 可以瘦身。**S**：`PetweenSettings.tsx` SaveIndicator（:150-159）。
3. **「未保存」一词只留给 dirty。** 身份无归属一律称「未命名」（§4）；notice/hint/确认文案全局排查统一。**S**：`PetweenSettings.tsx`、`editor-store.ts` 文案常量。
4. **破坏性确认必含对象名与后果三元组**（删什么、什么随之消失、什么保留）。删除确认按 §2.4 文案；导入确认现状已含丢弃说明（`editor-store.ts:766`），维持。
5. **禁用态必须给得出原因。** 生效行删除禁用 → 行内说明（§2.4）；导出/署名在「未命名配置」下禁用 → 维持现状 warn（`editor-store.ts:713-715, 826-828`），文案随原则 3 统一。

### 5.3 各操作的位置说明

- **另存草稿为新宠物**：生命周期里唯一的「无损分叉」，dirty 可用、不切换（A2 拍板语义，`routes.ts:653-656`）。在动线里属于「使用」区动作、产出落到「创建」。它是 dirty 阻止提示的指定出路（§3.3）。
- **重命名**：身份维护，随时可做；活跃目标走 dirty 门（保存语义混入名字变更会意外），非活跃免疫（现状 `editor-store.ts:957-963`，维持）。
- **导入**：创建入口，确认丢弃 dirty（维持）。**导出**：分享动作，对象恒为已保存预设——「未命名配置」下不开放草稿直接打包，维持 warn 引导先另存（理由：包是分享物，署名与名字是其一等元数据，草稿直出会绕开命名环节）。
